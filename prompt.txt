Build a polished, production-quality frontend for the existing iShop electronics e-commerce microservice application.

The current frontend is weak, so redesign it substantially. The result should feel like a real electronics storefront with a separate, professional admin experience—not a generic dashboard template.

## Stack and constraints

- Next.js with React and TypeScript
- Tailwind CSS and shadcn/ui (or the project’s existing component system)
- Lucide icons
- Recharts only where charts materially improve the admin experience
- Frontend origin: http://localhost:3001
- Backend gateway base URL: http://localhost:8080
- Keep API access in a typed service/client layer; do not scatter fetch calls through components.
- Inspect the backend source and OpenAPI definitions before implementing request/response types. Do not invent endpoints, fields, filters, or order workflows.
- Use the existing project structure when possible and preserve working setup/configuration.
- Use realistic loading, empty, error, validation, and unauthorized states.
- Do not hide API failures behind fake data. Mock data is acceptable only for an intentional development fallback and must be clearly isolated.

## Authentication and authorization

Use these gateway endpoints:

- POST /api/auth/login
- POST /api/auth/register
- POST /api/auth/refresh

Implement a typed auth client that stores tokens safely for the current frontend architecture, sends Authorization: Bearer <access-token> for protected requests, and refreshes an expired access token once before signing the user out. Avoid refresh loops.

Registration and login must show backend validation errors clearly. After login, route users according to their role: customers go to the storefront/account area and administrators go to the admin dashboard. Never rely only on hidden navigation for authorization; protect routes in the client and handle 401/403 responses.

### 4. Public products page

Use GET /api/operations/products.
This endpoint is public and must be fetched without an Authorization header.

Build a polished catalog with responsive product cards, tasteful image treatment or generated placeholders when the API has no image field, name, price, stock/availability, and active status where appropriate.

Include client-side filtering and sorting based only on fields returned by the API. At minimum provide search by product name/SKU and useful price/availability controls when those fields exist. Create a separate protected admin shell at /admin with a dark navy sidebar, blue accent, compact but spacious content layout, responsive mobile navigation, breadcrumbs, user menu, and clear active states.

# iShop API Reference (for the frontend)

This section was generated from the backend source (controllers, DTOs, security configs,
service implementations). It is the source of truth for request/response shapes. Do not
call anything not listed here.

## 1. Basics

- Base URL: http://localhost:8080 (the gateway). Never call the service ports 6666/8888/9999/7777 directly.
- Allowed browser origins (CORS is handled only by the gateway): http://localhost:3001, http://127.0.0.1:3001
  (override with the gateway env var CORS_ALLOWED_ORIGINS).
- CORS allows methods GET, POST, PUT, PATCH, DELETE, OPTIONS; any request header; credentials; preflight cached 3600s.
- Auth is a Bearer token in the `Authorization` header. The gateway STRIPS the `Cookie`
  request header, so cookie-based auth will not work.
- Content-Type: application/json for all request bodies.
- IDs are UUID strings. Timestamps (`Instant`) are ISO-8601 UTC strings, e.g. "2026-11-06T08:21:13.021432300Z".
- Money (`BigDecimal`) is a JSON number, e.g. 1299.99. Format it on the client. Display the server's
  `lineTotal` / `totalAmount` rather than recomputing totals with floating-point math.
- There is NO pagination, sorting, or filtering on any list endpoint. Lists return a plain JSON array.
  Filter and sort on the client.
- No endpoint wraps its response in an envelope (no `{ data: ... }`). Responses are the DTO itself or an array of it.

## 3. Error responses

All services return this JSON body for handled errors:

```ts
interface ApiErrorResponse {
  timestamp: string;             // ISO-8601
  status: number;                // HTTP status
  error: string;                 // reason phrase, e.g. "Bad Request"
  message: string;               // human-readable, e.g. "SKU already exists", "Validation failed"
  path: string;                  // service-internal path, e.g. "/products" (no /api/... prefix)
  fieldErrors: Record<string, string> | null;  // only present for validation failures
}
```

| Status | When | Body |
|--------|------|------|
| 400 | Bean validation failed | message "Validation failed"; `fieldErrors` = { fieldName: message }. Nested list fields use paths like "items[0].quantity". |
| 400 | Business rule (duplicate email/SKU/name, insufficient stock, inactive product, bad refresh token) | message explains it; `fieldErrors` null |
| 401 | Wrong email/password on login | message "Authentication failed" |
| 403 | Missing, invalid, or EXPIRED access token on a protected endpoint | EMPTY body (no JSON) |
| 403 | Authenticated but lacking a permission (auth-service /users endpoints) | JSON, message "Access denied" |
| 404 | Entity not found by id | message e.g. "Product not found: <uuid>" |
| 409 | DB constraint violation (e.g. deleting a product/customer still referenced by an order) | message "Database constraint violation" |
| 500 | Unexpected error. Also returned for unknown paths when a token is sent, and for a malformed (non-UUID) id | message "Unexpected server error" |

IMPORTANT for the auth client: an expired access token produces 403 with an EMPTY body, not 401.
The refresh-once logic must trigger on 401 OR on 403-with-empty-body for requests that carried a token.
A 403 with a JSON body ("Access denied") is a real permission problem: do not refresh, show a forbidden state.
Validate route ids as UUIDs on the client so a bad URL shows "not found" instead of a 500.

## 4. Auth service: /api/auth

Tokens:
- Access token: JWT, lifetime 60 minutes (`accessTokenExpiresInSeconds` = 3600).
- Refresh token: JWT, lifetime 7 days, stored server-side, single use (rotated on every refresh).
- Logging in revokes ALL previous refresh tokens of that user, so logging in on a second device
  invalidates the first device's refresh token.
- There is NO logout endpoint and NO "current user / me" endpoint. Logout = delete the tokens on the client.
  Keep the `user` object returned by login/refresh as the current-user profile.
- JWT claims (decodable client-side, not a security boundary): `sub` (email), `userId`, `roles` (e.g. ["USER"]),
  `tokenType` ("ACCESS" / "REFRESH"), `iss` ("auth-service"), `iat`, `exp`.

Roles and permissions (seeded):
- ADMIN -> USER_READ, USER_WRITE, USER_UPDATE, USER_DELETE
- USER  -> USER_READ
- Default admin account for local dev: admin@local.test / Admin@1234!
- Registration always creates a USER. Route after login by `user.roles.includes("ADMIN")`.

### POST /api/auth/register  (public)
Request:
```ts
interface RegisterRequest {
  firstName: string;   // required, max 100
  lastName: string;    // required, max 100
  email: string;       // required, valid email, max 150
  password: string;    // required, max 100, "strong": at least 8 chars with at least one uppercase,
                       // one lowercase, one digit and one non-alphanumeric character
}
```
Response 201: `UserResponse`. NO tokens are returned: send the user to login, or call login with the same credentials.
Errors: 400 validation; 400 "Email is already registered".

### POST /api/auth/login  (public)
Request: `{ email: string; password: string }` (both required; email must be a valid email).
Response 200: `AuthResponse`.
Errors: 400 validation; 401 "Authentication failed" (wrong credentials, or a disabled/locked account).

### POST /api/auth/refresh  (public)
Request: `{ refreshToken: string }`
Response 200: a new `AuthResponse` with a new access AND a new refresh token. Replace both; the old refresh token is now revoked.
Errors: 400 "Refresh token is invalid" or "Refresh token is expired or revoked" -> sign the user out. Note: 400, not 401.

```ts
interface AuthResponse {
  tokenType: "Bearer";
  accessToken: string;
  refreshToken: string;
  accessTokenExpiresInSeconds: number;   // 3600
  refreshTokenExpiresInSeconds: number;  // 604800
  user: UserResponse;
}

interface UserResponse {
  id: string;                 // UUID
  firstName: string;
  lastName: string;
  email: string;
  enabled: boolean;
  accountNonLocked: boolean;
  roles: string[];            // e.g. ["ADMIN"] or ["USER"]
  permissions: string[];      // e.g. ["USER_READ"]
  createdAt: string;
  updatedAt: string;
}
```

## 5. Operation service: /api/operations

Security:
- PUBLIC (send no Authorization header): `GET /api/operations/products` and `GET /api/operations/products/{id}`.
- EVERYTHING ELSE requires a valid access token.
- This service does NO role checks: any logged-in user (including the USER role) is technically allowed to
  create/update/delete products, customers and orders. Restrict these screens to admins in the UI.

### Products

| Method | Path | Auth | Body | Response |

| GET    | /api/operations/products      | public | -                | 200 `ProductResponse[]`. Includes inactive products: filter on `active` for the storefront. |
| GET    | /api/operations/products/{id} | public | -                | 200 `ProductResponse`; 404 |

| DELETE | /api/operations/products/{id} | token  | -                | 200 `{ message: "Product deleted successfully" }`; 404; 409 if the product appears in any order (suggest setting active=false instead) |

### Orders  (token required)

| Method | Path | Body | Response |
|--------|------|------|----------|
| GET    | /api/operations/orders      | -                    | 200 `OrderResponse[]` |
| GET    | /api/operations/orders/{id} | -                    | 200 `OrderResponse`; 404 |
| POST   | /api/operations/orders      | `OrderRequest`       | 201 `OrderResponse` |
| PUT    | /api/operations/orders/{id} | `OrderUpdateRequest` | 200 `OrderResponse` |
| DELETE | /api/operations/orders/{id} | -                    | 200 `{ message: "Order deleted successfully" }`; 404 |

Business rules (enforced by the server):
- New orders are created with status COMPLETED immediately. There is no cart, checkout or payment step.
- The server computes `orderNumber` ("ORD-<epochMillis>"), `orderDate`, each item's `unitPrice` (the product's
  current price), `lineTotal` and `totalAmount`. Do not send them.
- Creating an order DECREMENTS each product's `quantityInStock`. Errors: 400 "Insufficient stock for product: <name>",
  400 "Product is inactive: <name>", 404 if a customerId or productId does not exist.
- PUT replaces ALL items and sets the status: the old items' stock is restored, then the new items are deducted again.
  Setting status CANCELLED does NOT return stock by itself (stock stays deducted for the items you send).
- DELETE restores stock for all of the order's items.
- After any order mutation, refetch products if you display stock.

```ts
type OrderStatus = "PENDING" | "COMPLETED" | "CANCELLED";

interface OrderItemRequest {
  productId: string;   // required UUID
  quantity: number;    // required, integer > 0
}

interface OrderRequest {
  customerId: string;          // required UUID (an operation-service customer, not an auth user)
  items: OrderItemRequest[];   // required, at least 1
}

interface OrderUpdateRequest {
  status: OrderStatus;         // required
  items: OrderItemRequest[];   // required, at least 1 (full replacement)
}

interface OrderItemResponse {
  id: string;
  productId: string;
  productName: string;
  quantity: number;
  unitPrice: number;
  lineTotal: number;
}

interface OrderResponse {
  id: string;
  orderNumber: string;
  orderDate: string;
  totalAmount: number;
  status: OrderStatus;
  customer: CustomerResponse;   // full customer embedded
  items: OrderItemResponse[];
  createdAt: string;
  updatedAt: string;
}
```

## 6. Reporting service: /api/reports  (token required; no role checks, so admin UI only)

The GET endpoints compute live aggregates and take no parameters (no date range).

| Method | Path | Response |
|--------|------|----------|
| GET  | /api/reports/products        | `ProductReportResponse` |
| GET  | /api/reports/orders          | `OrderReportResponse` |
| GET  | /api/reports/customers       | `CustomerReportResponse` |
| GET  | /api/reports/sales           | `SalesReportResponse` |
| POST | /api/reports/products/store  | `ReportStoredResponse` (saves a snapshot; no request body) |
| POST | /api/reports/orders/store    | `ReportStoredResponse` |
| POST | /api/reports/customers/store | `ReportStoredResponse` |
| POST | /api/reports/sales/store     | `ReportStoredResponse` |

There is no endpoint to list or read stored snapshots; you only get back the id, type and time.

```ts
interface ProductReportResponse {
  totalProducts: number;
  activeProducts: number;
  totalStockQuantity: number;
  averagePrice: number;          // 2 decimals
}

interface OrderReportResponse {
  totalOrders: number;
  completedOrders: number;
  cancelledOrders: number;
  totalSales: number;            // sum of ALL orders, including cancelled ones
  averageOrderValue: number;     // 2 decimals; 0 when there are no orders
}

interface CustomerReportResponse {
  totalCustomers: number;
  distinctCustomerEmails: number;
}

interface SalesReportResponse {
  totalRevenue: number;                // sum of ALL orders, including cancelled ones
  totalOrders: number;
  bestSellingProduct: string | null;   // product on the single largest order line; null if no orders
  bestSellingQuantity: number;         // quantity on that one line (not a per-product total)
}

interface ReportStoredResponse {
  id: string;
  reportType: "PRODUCTS" | "ORDERS" | "CUSTOMERS" | "SALES";
  generatedAt: string;
}
```

CAVEAT: reporting-service reads its OWN database (port 5434), separate from operation-service's database (port 5433).
Report numbers may not match the live /api/operations lists. Label them as reports, and don't compute KPIs by
mixing the two sources.

## 7. Cron service: /api/jobs  (token required; no role checks, so admin UI only)

### GET /api/jobs/status
```ts
interface CronStatusResponse {
  lastMinuteRun: string | null;        // runs every minute (system summary)
  lastMidnightRun: string | null;      // daily at 00:00 server time (daily sales)
  lastSundayRun: string | null;        // Sundays at 00:00 (archives audit logs older than 30 days)
  lastMinuteReportId: string | null;
  lastMidnightReportId: string | null;
  lastSundayReportId: string | null;
}
```
Status is kept in memory: each field is null until that job has run since the cron service last started
(midnight/Sunday are usually null right after a restart). Render null as "Not run since restart", not as an error.
There are no endpoints to trigger jobs or to read their reports.

## 9. Endpoints that do NOT exist (don't build UI that depends on them)

- Logout, current user ("me"), change password, forgot/reset password
- Creating a user other than via /register; listing roles or permissions
- Customer-facing "my orders", or any link between auth users and customers
- Cart, checkout, payment
- Product images, categories, and search/filter/pagination query parameters
- A status-only order update (PATCH): status changes go through the full PUT
- Listing stored reports, or triggering cron jobs
